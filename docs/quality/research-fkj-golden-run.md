## 当次暴露并随后修复的问题

1. 首次运行的长 JSON 工具调用被兼容层 4096 token 默认值截断。研究策略现显式透传模型档案的原生最大输出，
   DeepSeek V4 Pro 为 393,216；Tessera 不另设抽象 token 预算。
2. 供应商产生 15,552 条逐 token 事件，数据库已完成但 renderer 长时间追赶。主进程现按 ID 和类型合并正文、推理与
   工具参数增量，在非增量事件与结束前强制刷新；语义顺序、完成指标和审计事件保持不变。
3. 失败后的“重试”原来只是新请求。现在重新生成携带目标消息，主进程通过持久化 `requestId` 解析 provenance，
   克隆计划、来源状态、证据、推荐和覆盖结果；网页全文不克隆，需要新增摘录时必须重新读取。
4. 当次 renderer 背压还造成数据库已有完整终态事件、但助手消息未及时落盘。恢复协议现会识别未被任何助手消息
   `requestId` 引用的最新运行，重放终态事件并保存报告；保存完成后同一运行不再重放。实际桌面 UI 已从这份事件
   账本恢复完整报告、研究进度、两条来源推荐和运行信息。历史 15,552 条事件仅在回放快照中临时合并，原始审计
   序列保持不变。
5. 完成态研究的纯文本续跑不需要重复调用 `finalize-research`。黄金审计现允许从有 provenance 的祖先继承完成检查，
   但仍只统计当前 run 的最终正文；这样既不重放工具副作用，也不能拿祖先报告冒充本轮交付。

来源保存的权限边界也已验证：推荐只呈现勾选项，不会自动创建文件；内容库或工作区不可用时返回可见失败，不回退到
任意本地路径写入。确定性测试使用临时真实内容库验证了“选择前零写入、选择后生成带证据定位的 Markdown、重复保存
复用同一 Artifact”。
