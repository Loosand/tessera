## 地位

本文分开记录两类结论：已经确认的 AI 协作交互，以及尚未确认的内容存储方案。用户只进行自然对话，系统在
每一轮按需直接回答、研究、调用 Skill、创建文档或整理项目；Chat 与 Agent 不再是用户需要理解或提前选择的
产品模式，二者收敛为同一个 Agent 运行时在不同请求下的行为结果。

内容最终以数据库、托管内容库中的 Markdown，还是用户任意添加的工作区为主要事实源，当前仍需通过原型和
真实使用验证。探索期间继续遵守仓库现有约束：Markdown 是已批准正文事实源，SQLite 只负责控制层；未经新的
架构决策与迁移设计，不得提前把正文改为数据库事实源或建立双事实源。

## 已确认的交互原则

1. **单一对话入口**：新任务、工作区任务和文档侧栏最终都使用同一套消息、运行与工具协议。
2. **默认使用 Agent 运行时**：每轮由 AI SDK `ToolLoopAgent` 执行；无需工具时直接生成正文，不能为了证明
   “正在使用 Agent”制造搜索或工具调用。
3. **创作方式是逐轮快捷提示**：默认由 Agent 自动编排；研究、写作、问答只覆盖之后发起的运行，不在会话首次
   保存后锁定，也不把一个 Task 变成不可切换的“模式”。
4. **Skill 按轮次选择**：用户可以在同一会话中从普通问答自然进入研究或写作；实际使用的 Skill 固化到
   对应 `task_run`，保证历史可解释，但不固定整个 `task_session`。
5. **上下文动态关联**：任务可以从无工作区开始，随后附加当前文档、关联一个或多个工作区、创建新项目并
   切换当前作用域，不需要新建或复制对话。
6. **业务工具隔离存储实现**：模型调用“创建项目”“创建文档”“移动文档”等领域工具，应用服务再将其映射为
   当前选定的存储后端；模型不依赖数据库表、绝对路径或任意文件系统能力。
7. **存储选择不泄漏到交互**：无论实验采用数据库、托管内容库还是外部工作区，用户看到的 Task、Project、
   Document、Artifact 和 Operation 语义保持一致。
8. **任务随创作过程延续**：通过 Artifact 打开或移动到其他项目只改变当前资源作用域，不重置 Task；文档侧栏
   显示当前任务、项目历史和新建入口，并与主任务页共用消息、reasoning、工具和恢复协议。

## 目标交互

同一条任务需要支持以下连续流程：

```text
用户提出普通问题
  -> Agent 判断是否需要联网
  -> 直接回答或搜索后回答
用户要求深入研究并写成文章
  -> 本轮自动选择研究/写作 Skill
  -> 只在核心方向确有歧义时发布一次结构化问题
  -> 搜索、阅读材料并创建 Document Artifact
  -> 对话与新文档进入左右协作视图
用户要求建立独立项目
  -> Agent 提议项目名称和目标位置
  -> 通过当前存储适配器创建 Project
  -> 安全移动新文档、更新关联和索引；混合实验对应本地目录操作
  -> 验证项目结构并在原对话中继续工作
```

用户不需要在流程开始时决定 Chat/Agent，也不需要手动打开联网、工具调用或思考强度。用户明确选择研究、
写作或问答时，选择只覆盖之后发起的运行；未选择时使用自动策略。生成期间也可以先调整选择，已经开始的 run
保持冻结策略，后续新 run 读取新的选择。

## 运行时编排

### 每轮策略解析

每次用户提交都先由受信任的运行策略解析器生成 `RunPolicy`。当前第一版已经以主进程持久化的模型事实、显式创作
方式、当前轮用户文本和眼下已授权工作区生成端点、联网、推理、工具作用域及预算；renderer 只做同源预检，
不再通过 IPC 决定联网或思考强度。自动方式只识别明确的研究/写作意图，项目整理保持自动并交给领域工具；
显式模式始终优先，模型能力不足时自动研究回落为普通自动策略。完整输入边界为：

- 用户对之后运行的显式创作方式提示；
- 当前会话历史和已持久化工具结果；
- 可见、可移除的附件与当前文档上下文；
- 当前关联工作区及主进程已经确认的授权范围；
- 当前供应商、模型和端点的已验证能力；
- 全局权限设置、资源限额和待审批状态。

输出至少包括实际模型路由、reasoning 策略、联网策略、Skill、可注册工具、步骤/时间/token 上限和审批策略。
模型提示词、Skill 或历史消息不能自行扩大这些能力。

```text
Task + User Turn + Visible Resources + Model Facts + Permissions
                         |
                         v
                resolveTaskRunPolicy()
                         |
                         v
          ToolLoopAgent(toolChoice = auto)
              |          |           |
              |          |           +-> 领域工具 -> 主进程服务
              |          +-> 原生搜索 -> 来源 Part
              +-> 零工具直接回答
```

AI SDK 的 step 属于一次 `task_run` 内部执行细节。一个 run 可以连续调用多个工具，也可以在第一步直接输出文本；
Task、Run 和 AI SDK step 不能共用一个状态语义。

### AI SDK 标准优先约束

实现统一运行时前，必须针对仓库实际安装的 AI SDK 版本检查随包发布的 `docs/` 与 `src/`，不能依据旧版记忆
重新实现 SDK 已有能力。当前 `ai@7.0.73` 已提供以下标准路径：

| 需求 | 优先使用的 AI SDK 能力 | Tessera 只补充的边界 |
| --- | --- | --- |
| 多步 Agent 循环 | `ToolLoopAgent`、默认 `toolChoice = auto` | 领域 instructions、资源权限和产品工具 |
| 每轮动态配置 | `callOptionsSchema` + `prepareCall` | 把已解析 `RunPolicy` 作为类型化 options 传入 |
| 每步收窄工具/模型 | `prepareStep`、`activeTools`、`stopWhen` | 预算、权限上限和领域完成条件；不得在 step 中扩大授权 |
| 受限工具 | `tool()`、`inputSchema`、`contextSchema`、`toolsContext` | 主进程领域服务、路径/记录校验和稳定资源 ID |
| 动态审批 | 工具 `needsApproval` / `toolApproval`，必要时由 `prepareCall` 返回本轮策略 | 审批 UI、SQLite 冻结、版本复核和本地审计 |
| 对话消息 | `UIMessage`、`InferAgentUIMessage`、`convertToModelMessages` | 应用元数据 schema、持久化和旧版本迁移 |
| React 会话状态 | `useChat` 与标准 Tool Part 状态 | Tessera 视觉组件和任务导航 |
| UI 流 | Agent `stream()` / UI message stream 与标准 chunk | Electron 主进程事件持久化、恢复和 IPC 背压 |
| 运行观测 | `onStart`、`onStepStart`、`onToolExecutionStart/End`、`onStepEnd`、`onEnd` | 本地指标、审计关联和公开错误映射 |
| 子任务 | AI SDK 子 Agent / tool 组合模式 | 只读或专用权限边界，不自建第二套编排协议 |

`DirectChatTransport` 适合单进程桌面或测试，但当前版本不支持 stream reconnect。Tessera 的 renderer 与主进程隔离，
且已经要求页面离开后恢复后台运行，因此生产链路继续实现标准 `ChatTransport` 接口的 Electron 适配器；它只负责
IPC 与重连，不得复制 `useChat` 状态机、UIMessage 转换或 Agent loop。`DirectChatTransport` 可以用于无重连需求的
单元/集成测试。

`runtimeContext` / `toolsContext` 可以携带主进程已经解析的稳定 ID、权限和服务句柄，但敏感值不能进入模型消息。
AI SDK memory、WorkflowAgent 或实验性 API 只有在验证桌面进程生命周期、离线数据边界、许可证和迁移成本后才能
采用；当前 Task/Message/Run 持久化不能为了追随某个供应商 memory 而失去应用事实源。

新增抽象必须先证明标准能力存在缺口。以下内容禁止平行自建：Agent 循环、工具状态机、审批状态语义、消息 Part
协议、模型消息转换和 React chat 状态。现有 `AgentRuntime` 只保留为承载标准 `UIMessageChunk`、`AbortSignal` 与
Electron 边界的薄端口，不能演化成第二套 Agent 框架。若确需偏离标准方案，实施 PR 必须记录当前 SDK 版本、
查过的 docs/source、缺口、替代方案、退出路径和回归测试。

### 创作方式与能力分层

输入框中的入口是一个混合快捷面板，不是一组互斥且不可逆的系统模式。当前分层如下：

- “自动”表示没有显式覆盖，由 Agent 按请求和可用能力编排。
- “研究”“写作”是内置 Skill 的快捷入口，同时带出受信任的 RunPolicy 默认值。
- “问答”只是关闭联网和主动项目操作的回答预设，不伪造一份 Skill。
- 图片、视频、幻灯片、网页等属于输出能力、工具或专用模型路由；接入后可以和 Skill 共存，但不能为了塞进同一
  菜单就扩张成 `TaskSkillId`，也不能把用户锁进新的会话模式。当前只呈现已经打通的能力。

AI SDK `ToolLoopAgent` 通过每次调用的 `callOptionsSchema` / `prepareCall` 读取这些选择。一次 run 开始后策略冻结，
界面仍允许用户切换，新的值只影响之后发起的 run，不能回写正在执行的调用。

| 快捷选择 | 默认运行策略 | 边界 |
| --- | --- | --- |
| 未选择 / 自动 | 根据意图、资源和模型事实决定是否搜索、加载 Skill 或使用工具 | 只能在已有授权范围内自动化 |
| 研究 | 深度推理、原生联网、来源核验、必要时研究计划 | 缺少可靠联网能力时明确阻止或请求改用自动，不伪造研究 |
| 写作 | 加载写作 Skill，读取显式材料，允许提出或创建 Markdown 产物 | 不自动获得未授权目录或覆盖现有正文的权限 |
| 问答 | 不联网，不主动操作项目或文件，使用会话和显式附件直接回答 | 仍使用同一 Agent runtime，不另建 Chat 实现 |

自动方式需要按当前用户 turn 识别意图。例如会话前几轮只是人物问答，后续“写成一篇自媒体稿”应让下一次
run 加载写作 Skill；过去的 run 保留当时实际策略，不被回写。

## 内容存储探索

最终方案尚未决定，当前保留三个候选：

| 候选 | 正文事实源 | 优势 | 主要代价 |
| --- | --- | --- | --- |
| 数据库方案 | SQLite/其他数据库中的文档记录 | 创建、移动、关联、撤销与多端同步最简单 | 外部编辑、Git、普通文件备份和用户直接拥有感变弱，需要完整导入导出与灾难恢复 |
| 托管内容库混合方案（当前实验基线） | 用户选择根目录中的 Markdown；SQLite 保存控制关系 | 兼顾稳定项目 API、本地文件所有权和可移植性 | 必须处理路径、外部修改、移动冲突和数据库关系刷新 |
| 完全开放外部工作区 | 用户任意添加目录中的 Markdown | 最符合现有文件习惯，不要求托管目录 | 自动创建/整理项目、跨目录移动和权限解释最复杂 |

当前暂用托管内容库混合方案推进原型，因为它能验证统一 Agent 的完整交互，同时保持可逆：普通 Markdown 可以
导出或直接迁移，领域工具协议也能在后续替换存储适配器。这个选择不是最终产品承诺。

进入不可逆实现前，需要用真实任务评估：首次设置成本、无工作区开始的成功率、文档创建/移动失败率、外部编辑
冲突、备份恢复、导入导出、多端需求、用户对文件所有权的重视程度，以及数据库/文件迁移成本。当前指标、证据与
最终门槛记录在 [ADR-0001：内容存储实验基线与评审门槛](adr-0001-content-storage-experiment.md)；它仍是提议，
不代表最终选型。

## 产品对象与当前混合基线映射

| 产品对象 | 用户心智 | 本地实现 |
| --- | --- | --- |
| Task | 一条可以持续推进的对话 | SQLite 会话和版本化消息 |
| Run | 一次用户提交触发的执行 | SQLite 运行、策略快照和有序事件 |
| Workspace / Project | 一个长期项目容器 | 已登记的本地目录；公共 `ProjectRef` 不暴露后端位置 |
| Document | 可继续编辑和交付的内容 | Markdown 文件；公共 `DocumentRef` 只使用稳定 ID 和项目关系 |
| Artifact | Agent 在某个 run 创建或修改的产物关系 | `artifacts` 保存稳定身份，文档移动不改变 Artifact ID |
| Resource Binding | 当前对话可以使用的材料与作用域 | `task_resource_bindings` 保存逐轮附件、文档、项目及 output/scope/context 角色 |
| Operation | 创建、移动、重命名或写入动作 | 主进程文件操作 + SQLite 审计 |

### 当前混合基线的内容层与控制层

```text
内容层（用户资产）                 控制层（应用状态）
Markdown / 图片 / 附件             Task / Run / Message
本地目录 / 外部编辑器 / Git         Workspace 登记 / Artifact 关联
可复制、同步、备份和独立打开         索引 / 权限 / 审批 / 操作审计
```

探索期间 SQLite 不能成为已批准 Markdown 正文的唯一副本。候选内容可以在审批期间冻结到数据库；批准后必须
写回本地文件。若数据库丢失，正文仍可读取；会话关系和审计不一定可重建，因此仍需要正常备份数据库。若最终
选择数据库正文，必须先以新 ADR 替换此边界并设计导入、导出、备份、恢复与迁移。

### 内容库与 Inbox

作为当前混合方案实验，为支持无需预选工作区的自然流程，已经实现一个用户明确选择的“Tessera 内容库”根目录：

- 用户从设置页选择或创建内容库根目录；选择结果成为可撤销授权，不静默使用任意系统目录。
- 根目录下维护一个普通、可见的“未归档”工作区。无项目任务创建的新文档默认进入这里。
- 用户可以继续把内容库外的任意目录登记为外部 Workspace；外部目录不会被强制搬入内容库。
- 在内容库内创建项目只创建普通子目录和 Workspace 登记，不引入只能由 Tessera 读取的专有容器。
- 对话本身仍保存在 SQLite，可以关联或切换 Workspace，不需要把聊天 JSON 写入项目目录。

若用户只进行问答，系统不应为了给 Task 寻找归属而创建空目录或空文档。

## 后端无关的领域工具

模型只获得面向产品对象的窄工具。工具输入优先使用稳定 ID 和名称；混合/外部工作区适配器额外使用经校验的
工作区相对路径，主进程闭包持有真实根路径。数据库适配器可以映射为记录操作，但不能改变工具的产品语义。

| 工具 | 作用 | 关键约束 |
| --- | --- | --- |
| `list-workspaces` | 列出已授权项目和 Inbox | 不返回绝对根路径 |
| `read-workspace-document` | 读取已关联工作区 Markdown | 复用真实路径、扩展名、符号链接和大小校验 |
| `read-current-document` | 读取用户可见附加的编辑器草稿 | 使用最新草稿，不能静默读取旧磁盘版本 |
| `create-document` | 在 Inbox 或目标 Workspace 创建新 Markdown | 只允许 create-new；重名时返回冲突，不覆盖 |
| `update-document` | 提出现有 Markdown 的完整候选内容 | 冻结基准和候选，经过 Diff/审批后原子写入 |
| `create-workspace` | 在已授权内容库内创建项目目录并登记 | 校验名称、父目录和现有路径；外部位置需要系统选择器授权 |
| `move-documents` | 在 Workspace 间移动一个或多个文档 | 预检冲突、更新关联和索引、记录来源/目标并提供恢复信息 |
| `inspect-workspace` | 验证目标项目结构和产物位置 | 只读，不把完整目录树塞入模型上下文 |

第一版不向模型开放任意 Shell、绝对路径、递归删除、任意文件类型或无边界的 `mkdir` / `mv`。领域工具内部可以
调用文件系统和数据库，但必须以单个主进程应用服务协调，避免 Agent 分别修改两边造成状态漂移。

文件操作优先遵守以下顺序：先预检路径与冲突，再执行可恢复的本地操作，最后更新 SQLite 关系并触发索引刷新；
数据库更新失败时，以磁盘事实为准重新扫描，不能为了恢复索引而覆盖或删除用户文件。

## 资源关联与上下文

- Task 不再永久绑定单一 Workspace；它可以没有作用域，也可以在运行中关联多个资源。
- 每个 run 固化本次实际可见的资源清单，保证历史恢复和审计能够解释模型看到了什么。
- “当前文档”必须继续以可见、可移除的附件呈现；进入文档侧栏可以默认附加，但用户能在发送前移除。
- Agent 创建文档后，Artifact 自动加入当前会话上下文，并可在同一 TaskPage 中打开左右协作视图。
- 创建新项目并移动 Artifact 后，Task 的当前作用域切换到新 Workspace；旧 run 的资源快照保持不变。
- 任务列表可以按 Workspace 聚合展示同一 Task，但 Task 的数据库身份和历史不因项目移动而复制。

## 权限、预览与审计

统一运行时不等于统一放权。权限根据资源和动作判断，而不是根据 Chat/Agent 标签判断。
下表描述当前托管内容库混合实验的默认交互；若切换存储适配器，授权目的、可见预览、冲突和审计语义必须保持，
具体“文件”动作再映射为对应后端操作。

| 动作 | 默认交互 |
| --- | --- |
| 读取显式附件和已授权工作区 | 自动执行，活动轨迹显示实际资源 |
| 联网搜索 | 由本轮创作策略决定，展示真实查询与来源 |
| 新建不覆盖的 Markdown | 用户明确要求创建内容时，该请求构成目的授权；仍展示实时产物预览并记录操作 |
| 修改现有 Markdown | 必须展示候选渲染和源码 Diff，批准后复核版本再写入 |
| 在内容库内新建项目 | 用户明确要求或选择推荐方案后执行，显示目标并记录结果 |
| 移动/重命名文件 | 明确指令或确认过的结构化选项才执行；先检查冲突，显示来源和目标并保留恢复信息 |
| 删除、覆盖、内容库外写入、Shell | 使用独立高风险权限面；未实现前保持不可达 |
| MCP 工具 | 只注册用户显式信任、启用且未逐项停用的工具；每次调用仍人工批准，不继承内容库权限 |

结构化问题只用于会改变核心结果、且无法安全推断的选择。用户已经说“建立单独项目”时，不应再次询问是否真的要
建立项目；项目名称或位置只有在多个候选同样合理且会影响本地组织时才询问一次。

## 界面约束

- 输入框不显示 Chat/Agent、联网、工具调用或思考档位开关；只保留附件、创作方式、模型和发送。
- 创作方式默认显示“自动”，运行前、运行中和运行后均可切换；已经开始的 run 保持原策略，新选择从之后发起的
  run 生效。
- 运行过程按真实事件折叠为活动时间线：思考、搜索、读取、提问、创建文档、创建项目、移动文档和验证结构。
- 供应商没有返回可展示 reasoning 文本时，将同一回复内的空 reasoning 生命周期聚合为一个紧凑“思考中 / 思考完成”阶段，不显示占位正文或无效展开按钮；非空 reasoning 仍按原始 Part 展示，工具活动由工具 Part 表达。
- 文档创建后自动进入对话 + Artifact 的左右协作视图；关闭侧栏不丢失会话、运行或附件关系。
- 文件操作结果使用面向用户的对象名称和相对位置，不把 API schema、数据库表名或绝对路径作为主要文案。
- 错误应说明哪个动作没有完成以及文件当前真实位置，不能只显示模型或工具内部异常。

## 持久化目标与迁移

### 当前混合基线的数据职责

- `task_sessions`：会话身份、标题、状态和时间，不再以 mode/Skill/单一 Workspace 定义整个会话权限。
- `task_messages`：用户、助手和工具的版本化消息 Part。
- `task_runs`：每轮实际模型、创作策略、Skill、联网/工具策略、资源快照摘要、完成原因、用量和耗时。
- `content_libraries`：当前授权内容库及撤销时间；撤销只移除授权，不删除用户文件。
- `task_resource_bindings`：Task/Run 与 Workspace、Document、Attachment 的动态关系和角色；同一 Task 最新 scope
  关系表示当前项目，旧 run 关系保持不变。
- `artifacts`：Agent 产物的稳定 ID、当前文档关系、创建 run 和状态。
- `workspace_operations`：创建文档/项目、移动文档和结构检查的参数、结果、冲突与恢复信息。
- `agent_change_proposals`：保留现有正文候选、Diff、决定和写入结果。

### 兼容迁移

1. 已发布的 `task_sessions.mode`、`skill_id` 和 `workspace_id` 不原地改写或删除。
2. 读取旧任务时把这些列解释为初始运行策略和初始资源绑定；历史仍按旧权限恢复。
3. 新运行开始时把实际策略和资源固化到 `task_runs` 及新增关系表，不再依赖会话级不可变字段。
4. 所有入口切换到统一 Agent runtime 后，再停止创建新的 `chat` 会话；旧 mode 仅用于兼容读取和审计。
5. 迁移只新增 SQLite schema 和关系，不把现有 Markdown 正文导入数据库。

## 探索与实施顺序

1. **AI SDK 能力审计**：基于锁定版本建立需求到 `ToolLoopAgent`、`prepareCall`、`prepareStep`、`toolApproval`、
   `InferAgentUIMessage`、`ChatTransport` 和生命周期回调的映射；删除重复抽象的设计，不先写新框架。
2. **统一运行入口（已完成基础切换）**：所有任务都通过 `ToolLoopAgent`，并共用 `task-agent.ts` 的类型化 call
   options / `prepareCall`；无资源时只注册对话、可用联网和结构化交互工具，允许零工具回答。
3. **按 run 保存策略与指标（已实现）**：创作方式可逐轮切换，主进程生成类型化 RunPolicy；`task_runs` 同时
   保存兼容查询列、完整 `policy_json`、不含正文/绝对路径的 `resource_summary_json`，以及 AI SDK 生命周期提供的完成原因、
   Token/缓存、步骤/工具计数和耗时汇总，旧任务继续保持未知值兼容；规范化关系另存实际逐轮资源。
4. **动态资源绑定（已实现）**：引入 Task/Run 到 Workspace、当前文档和附件的关系；文档侧栏与完整任务页继续复用
   同一 Task。
5. **领域工具（已实现）**：实现 `create-document`、`create-project`、`move-documents` 和结构验证的主进程应用服务、
   IPC、审计与冲突测试。
6. **内容库与 Inbox 实验（已实现原型）**：增加可撤销根目录选择、默认未归档工作区和外部 Workspace 并存规则；所有数据
   保持普通 Markdown，可完整导出和移除授权。
7. **存储决策评审**：用端到端任务和恢复演练比较数据库、托管内容库与完全外部工作区，形成独立 ADR；
   评审前不做不可逆正文迁移。
8. **产物协作界面（已实现基础闭环）**：Artifact 卡片可打开文档 + 原 Task 侧栏，移动后追加新的 scope 关系；
   完整 Operation 活动聚合仍需继续打磨。
9. **收敛旧模式（部分实现）**：用户路径和模型运行已无 Chat/Agent 选择；历史 `mode/workspace_id` 仍用于兼容归属，
   当前轮是否注入工作区工具只由眼下打开且已授权的工作区决定。

实施时每一步都必须保持现有 Markdown 路径防护、Diff 审批、运行恢复和人工编辑路径可用。不能用一次性大迁移同时
替换运行时、数据库和文件操作。

## 验收场景

1. 用户在无工作区的新任务询问普通知识，Agent 不调用文件工具即可直接回答。
2. 同一会话下一轮要求深入研究，系统自动联网、显示来源，并保留上一轮历史。
3. 再下一轮要求写文章，系统加载写作 Skill、必要时只问一次核心问题，并创建可见 Document Artifact；当前混合实验将其落为 Markdown。
4. 用户要求建立独立项目后，系统通过当前适配器创建 Project、移动 Artifact、更新上下文并验证目标结构；混合实验在授权内容库内创建 Workspace 目录。
5. 整个流程没有 Chat/Agent 选择，也不要求用户理解工具开关；每个 run 仍可审计实际模型、Skill、资源和动作。
6. 当前混合实验中，应用退出重启后，对话、活动、Artifact 和目标 Workspace 可以恢复；Markdown 可脱离 Tessera 单独打开。
7. 当前混合实验中，数据库索引异常不会覆盖、删除或隐藏磁盘上的已批准正文。
8. 同一组交互验收能够针对数据库或外部工作区适配器复用，用于最终存储评审。

## 非目标

- 不在探索结论前把任一存储候选写成最终架构，也不执行不可逆正文迁移。
- 不同时把数据库正文和 Markdown 正文都声明为权威副本。
- 不让 Agent 通过自然语言自动获得任意文件系统权限。
- 不因为统一运行时而强制每轮深度思考、联网或调用工具。
- 不在第一版开放递归删除、任意 Shell 或跨设备协同写入；MCP 只通过独立服务器信任、逐工具开关与逐次审批接入，不能绕过资源边界。
- 不为复刻某个外部产品长期保存页面级对比；本文只记录 Tessera 已确认的交互原则、当前实现事实和待验证的存储问题。
