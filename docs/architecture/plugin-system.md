# 插件系统

> 代码源头：`apps/desktop/src/main/index.ts`、`apps/desktop/src/preload/index.ts`、
> `packages/contracts/src/index.ts`、`packages/skills/src/index.ts`、`packages/agent-runtime/src/index.ts`
>
> 状态：规划。Electron 渲染层沙箱、窄 IPC、工作区路径校验、内置 Skill 渐进式加载/权限描述和 Agent 权限事件已存在；
> 插件包协议、发现与安装、贡献点、插件运行容器、权限授权和社区目录均未实现。

## TL;DR

Tessera 的插件系统由五个相互独立的部分组成：插件包协议、贡献点注册、隔离运行时、能力与权限网关、安装更新系统。
插件不是把第三方 JavaScript 导入主进程或应用 React 组件树，而是一个经过校验的不可变包。宿主先读取清单并注册静态贡献，
只在命令、视图或文件类型真正被使用时启动插件。

普通社区插件运行在独立的沙箱化 WebContents 中，不具备 Node.js、Electron、任意文件系统、数据库或默认网络访问能力；
插件通过与运行容器绑定身份的 RPC 请求能力，主进程在每次调用时校验权限和资源范围。设置、菜单和简单界面优先使用声明式
贡献；完整自定义界面运行在隔离页面中，不进入宿主 DOM。需要 Git、外部进程或工作区外文件的可信桌面插件属于后续能力，
必须单独授权，不能成为普通插件逃逸沙箱的通道。

首个版本只建设本地开发插件、命令、声明式设置、通知、只读工作区和启停诊断。不建设社区市场，也不开放任意 Node.js、
Electron、原生模块和宿主 React 组件。经过内部插件验证 API 稳定性后，再增加编辑器扩展、侧边视图、受控写入和社区目录。

## 背景与设计问题

Tessera 需要让社区围绕真实工作流增加文件导入、阅读处理、写作辅助、可视化和第三方服务接入，而不要求核心应用长期维护
所有垂直功能。与此同时，插件是本地应用内的第三方可执行代码，可能接触用户文章、附件、密钥、网络和系统能力。一个只有
目录扫描与动态导入的实现会同时破坏下面几条现有边界：

1. 渲染层不直接访问 Node.js、文件系统或数据库。
2. 文件路径由主进程解析并限制在当前工作区内。
3. Agent 读取、联网、执行和写入分别授权。
4. Markdown 是正文事实源，插件不能持有无法导出的正文唯一副本。
5. 应用 UI 使用共享设计系统，第三方样式不能污染整个组件树。

因此，插件系统首先是安全边界和兼容协议，其次才是插件列表和安装界面。

## 概念与能力状态

| 概念 | 定义 | 状态 |
| --- | --- | --- |
| Skill | 可阅读、可修改的 `SKILL.md` 工作流与权限声明，不提供任意应用代码和 UI；内置研究/写作已按需注入模型 | 部分实现 |
| 插件包 | 清单、单文件逻辑包、可选隔离 UI、样式和文档组成的不可变发布物 | 规划 |
| 贡献点 | 命令、设置、菜单、视图、文件处理器等宿主认可的扩展位置 | 规划 |
| 标准插件 | 在无 Node.js 的隔离运行时中执行，只能调用授予的 Tessera API | 规划 |
| 可信桌面插件 | 明确获得系统级能力、风险更高的插件类型 | 待确定，不属于首个版本 |
| 本地开发插件 | 用户手动选择目录、允许重新加载的未发布插件 | 规划 |
| 社区目录 | 提供元数据、版本、哈希和下载地址的审核索引 | 待确定，不属于首个版本 |
| 插件市场 | 付费、榜单、推荐、分成和账户体系 | 非目标 |

Skill 与插件不能互相伪装。Skill 声明 Agent 工作流，权限仍由 AgentRuntime 和用户决定；插件扩展应用能力，必须经过插件运行时
和插件权限网关。插件触发 Agent 时，同时满足插件调用权限和 Agent 本次执行权限，不能用其中一种授权替代另一种。

## 目标与非目标

### 目标

1. 提供稳定、版本化且与 Tessera 内部实现解耦的插件 API。
2. 插件不进入主进程、预加载脚本或宿主 React 组件树执行。
3. 每个能力请求都能确定插件身份、授权来源、资源范围和结果。
4. 插件按需激活，禁用、更新、崩溃和卸载不会要求重启整个应用。
5. 简单贡献自动符合 Tessera 的设计 token、字号、间距和无障碍规则。
6. 插件包可检查、可验证、可回滚，升级不能静默扩大权限。
7. 插件数据与用户 Markdown 分离，卸载插件不会让正文不可读。

### 非目标

- 不兼容 Obsidian、VS Code 或浏览器扩展的插件 API。
- 不允许插件直接导入 `apps/desktop`、内部 Zustand/React 状态或未公开包。
- 不把 `node:vm`、普通 Web Worker 或未约束的 `utilityProcess` 当作安全沙箱。
- 不在首个版本开放 Node.js、Electron、shell、任意 Git 参数或原生模块。
- 不在首个版本建设付费市场、排行榜、推荐流或自动云端同步插件。
- 不保证插件可以任意改变应用布局、覆盖全局 CSS 或猴子补丁内部对象。
- 不允许工作区中出现插件代码后自动安装或执行。

## 总体架构

```text
插件包 / 本地开发目录
          |
          v
  插件安装与校验服务 --------------------> 用户插件目录
          |                                  |
          | 清单、版本、哈希、兼容性          | 不可变版本
          v                                  v
      插件管理器 ----------------------> 插件运行容器
      |       |                         独立沙箱 WebContents
      |       |                                  |
      |       +----> 静态贡献注册表               | 带身份 RPC
      |              |                            v
      |              v                      插件能力网关
      |       命令 / 设置 / 菜单                  |
      |       视图占位 / 文件类型                 +--> 工作区服务
      |                                           +--> 文档服务
      +----> 状态 / 日志 / 崩溃处理                +--> 网络代理
                                                  +--> 插件存储
                                                  +--> AgentRuntime
```

应用渲染层继续只访问 `window.tessera` 暴露的 `DesktopApi`。插件不共享这座桥，而使用单独的插件 RPC 协议。两个协议必须分离，
因为 `DesktopApi` 信任的是 Tessera 自己的渲染层，插件协议还要绑定插件身份、检查授权、限制资源并记录调用。

## 插件包协议

### 发布物

```text
example-plugin/
  manifest.json
  dist/
    main.js
  ui/
    index.html          # 可选，完整自定义视图使用
    ui.js               # 可选，必须是已打包的单文件依赖
  styles.css            # 可选，仅作用于隔离 UI
  README.md
  LICENSE
```

发布包禁止包含安装脚本、`node_modules`、原生二进制和运行时依赖解析。插件作者必须把第三方依赖打入发布物；标准插件代码采用
ES Module，不能保留裸模块导入。宿主不执行 `npm install`、`bun install` 或任何 `postinstall`。

### 清单

```json
{
  "manifestVersion": 1,
  "id": "com.example.document-history",
  "name": "文档历史工具",
  "description": "为当前文档提供额外的历史查看命令。",
  "version": "1.0.0",
  "author": "Example",
  "license": "MIT",
  "engines": {
    "tessera": ">=0.3.0 <0.5.0"
  },
  "main": "dist/main.js",
  "activationEvents": [
    "onCommand:document-history.open"
  ],
  "permissions": [
    {
      "capability": "workspace:read",
      "reason": "读取当前文档以展示历史入口。"
    }
  ],
  "contributes": {
    "commands": [
      {
        "id": "document-history.open",
        "title": "查看文档历史"
      }
    ],
    "settings": [
      {
        "key": "showRelativeTime",
        "type": "boolean",
        "title": "显示相对时间",
        "default": true
      }
    ]
  }
}
```

`manifestVersion` 控制清单语法，`engines.tessera` 控制宿主兼容区间，两者不能合并。插件 ID 发布后不可更改，首个版本限定为
反向域名形式的小写 ASCII 标识。清单由共享契约和运行时校验器同时验证，不能只依赖 TypeScript 类型。

### 安装位置

插件程序安装到 Electron `userData` 下，而不是用户工作区：

```text
Tessera userData/
  plugins/
    com.example.document-history/
      1.0.0/
        manifest.json
        dist/main.js
      current.json
  plugin-data/
    com.example.document-history/
```

工作区只保存启用状态和可移植配置，不保存或自动执行插件程序。打开别人分享的工作区时，即使其中引用了某个插件，也只能提示
用户自行安装。插件升级先安装到新的版本目录，验证和启动成功后原子切换 `current.json`；旧版本保留一个回滚窗口。

## 发现、激活与停用

### 启动流程

```text
扫描已安装版本
  -> 校验目录、清单与文件哈希
  -> 检查 Tessera 兼容区间
  -> 读取用户和工作区启用状态
  -> 注册静态贡献
  -> 等待 activationEvent
  -> 创建插件运行容器
  -> 建立带身份 RPC
  -> 调用 activate(context)
```

应用启动阶段只读取清单和注册静态贡献，不执行插件代码。首批激活事件为：

- `onCommand:<command-id>`：用户执行插件命令；
- `onView:<view-id>`：用户打开插件视图；
- `onFileType:<extension>`：用户打开对应文件；
- `onWorkspaceContains:<glob>`：工作区检测到明确特征；
- `onStartupFinished`：仅对确实需要后台启动且经过审核的插件开放。

多个事件只激活一次。并发触发共享同一个激活 Promise。激活设定超时，失败后贡献点保留但标记不可用并展示诊断，不循环重试。

### 插件入口

```ts
export interface TesseraPluginModule {
  activate(context: PluginContext): void | Promise<void>
  deactivate?(): void | Promise<void>
}
```

`PluginContext` 由宿主创建，不能由插件构造或序列化。注册命令、事件和资源时返回 `Disposable`；运行容器同时记录所有资源，
即使插件没有正确实现 `deactivate()`，停用时也会由宿主撤销订阅、命令处理器、定时任务和未完成请求。

插件禁用、升级、工作区关闭或应用退出时先停止接收新调用，取消可取消任务，限时调用 `deactivate()`，随后关闭运行容器。
插件不能阻止 Tessera 退出；尚未完成的插件写入必须服从现有文档保存与冲突协议。

## 运行时隔离

### 标准插件

标准插件在独立的沙箱化 WebContents 中运行，要求：

- `nodeIntegration: false`；
- `contextIsolation: true`；
- `sandbox: true`；
- 使用独立 session partition；
- 只加载 `tessera-plugin://<plugin-id>/` 自定义协议中的已安装文件；
- CSP 默认禁止网络、子 frame、外部媒体、动态代码和未授权脚本；
- 不暴露 `ipcRenderer`，只暴露窄幅插件 RPC；
- 插件身份由创建该 WebContents 的宿主记录，消息中的自报 `pluginId` 不作为授权依据。

主进程维护 `webContents.id -> pluginId -> installedVersion` 映射。每个 RPC 请求根据发送者查找身份，再检查能力、资源和参数；
关闭运行容器后立即撤销映射。这样插件不能通过伪造 ID 使用其他插件的授权。

标准插件的网络访问必须经过宿主网络代理。插件页面的直接 `fetch`、图片外链、WebSocket 和导航默认被 CSP 与 session 请求过滤拒绝。
网络能力按协议与域名授权，并由主进程执行超时、响应体上限、重定向限制和凭据脱敏。

### 为什么不使用其他隔离方式

- `node:vm` 不是不可信代码的安全边界。
- 普通 Web Worker 继承创建它的页面能力，不能单独解决宿主 DOM、网络和身份隔离。
- `utilityProcess` 提供进程与崩溃隔离，但其中运行的 Node.js 代码仍可能直接访问文件和系统能力。
- 把插件导入宿主 React 树会共享全局对象、样式、依赖版本和崩溃范围。

这些机制可以作为内部任务或可信插件的实现组件，但不能代替标准插件的能力网关。

### 可信桌面插件

需要系统 Git、工作区外文件、外部进程或原生库的插件无法通过普通沙箱完整实现。后续若引入可信桌面插件，应满足：

1. 使用单独的安装类型和醒目风险说明，不能通过普通权限升级静默获得。
2. 在独立进程中运行，不进入 Electron 主进程。
3. 展示外部目录、命令、网络目标和密钥用途，权限增加时重新确认。
4. 社区目录进行更严格的源码、依赖和发布物一致性审核。
5. 支持立即终止、禁用和回滚，不因插件失败影响文档保存。

首个版本不实现这一类型。Git Diff、提交等核心需求优先由 Tessera 自己的主进程服务提供窄能力，再决定是否向插件开放。

## 插件 API 与能力网关

### API 形状

```ts
interface PluginContext {
  readonly plugin: {
    id: string
    version: string
  }
  readonly commands: CommandApi
  readonly workspace: WorkspaceApi
  readonly documents: DocumentApi
  readonly ui: UiApi
  readonly storage: PluginStorageApi
  readonly secrets: SecretStorageApi
  readonly events: EventApi
  readonly agent: AgentApi
}
```

公开 SDK 只包含类型、清单 Schema、测试替身和构建辅助，不包含应用内部服务。插件 API 使用结构化可克隆的数据，不跨边界传递
DOM、Electron 对象、数据库连接、文件句柄或内部类实例。

### 权限

首批权限分类为：

| 权限 | 能力 | 首个版本 |
| --- | --- | --- |
| `workspace:metadata` | 当前工作区名称、文档列表和相对路径 | 规划 |
| `workspace:read` | 读取工作区内经过校验的 Markdown 与附件 | 规划 |
| `workspace:write` | 通过原子写入和冲突协议修改工作区文件 | 后续 |
| `workspace:watch` | 订阅工作区文件变化 | 后续 |
| `network:<origin>` | 通过主进程代理访问明确 origin | 后续 |
| `clipboard:read` / `clipboard:write` | 读取或写入剪贴板 | 后续 |
| `secrets:use` | 使用插件自己的安全凭据槽位 | 后续 |
| `agent:request` | 发起需要独立 Agent 权限判断的任务 | 后续 |
| `git:read` | 读取仓库状态、历史和 Diff | 后续 |
| `git:commit` | 暂存文件并提交，不隐含 push | 后续 |

`workspace:read` 只接受相对路径，主进程继续执行规范化、真实路径解析、工作区包含检查和文件类型限制。授权信息至少包含插件 ID、
版本、权限、作用域、决定来源和更新时间。权限拒绝返回类型化错误，不向插件暴露内部路径或堆栈。

插件更新新增权限或扩大网络 origin 时，保持旧版本启用，新版本进入「等待授权」状态。用户拒绝后继续使用旧版本；插件不能以
“修复更新”为由绕过重新授权。

### 写入与 Agent

普通插件获得 `workspace:write` 后仍不能直接写文件。所有修改经过现有文档版本校验和原子替换；涉及 Agent 生成、批量修改、
覆盖或恢复时，继续遵守 Diff、批准、审计和版本历史边界。插件权限只说明插件可以提出或调用该能力，不等于用户批准某次
Agent 写入。

## 贡献点与 UI

### 静态贡献优先

首批贡献点为：

- `commands`：命令 ID、中文标题、图标和可选快捷键建议；
- `settings`：布尔、文本、数字、枚举和安全凭据引用；
- `menus`：将已有命令放入宿主允许的菜单位置；
- `notifications`：通过宿主通知组件显示短消息。

这些界面由 Tessera 渲染，插件只提供数据和处理器，因此自动继承设计 token、字号、密度、键盘操作和无障碍语义。插件不能
通过设置 Schema 注入 HTML、脚本或任意 CSS。

后续贡献点包括：

- `sidebarViews`：侧边栏或详情栏中的隔离视图；
- `editorActions`：编辑器工具栏和命令，不直接修改 TipTap schema；
- `editorExtensions`：经过单独兼容协议封装的 TipTap 扩展；
- `markdownProcessors`：受限输入输出转换，不持有正文事实源；
- `fileHandlers`：声明可打开的扩展名和只读预览能力；
- `importers` / `exporters`：导入和导出管线。

编辑器扩展必须晚于命令和视图实现，因为它会影响 Markdown 往返、协同 schema、粘贴规则和文档兼容性，不能直接暴露当前
TipTap 实例作为长期 API。

### 完整自定义视图

需要 Excalidraw 一类完整应用界面的插件，在自己的隔离页面内渲染。宿主只提供视图容器、标题、尺寸、主题变量副本和 RPC：

```text
Tessera React 组件树
  -> PluginViewHost
      -> sandboxed plugin document
          -> 插件自己的 React / Canvas / SVG
```

插件页面不能选择或修改外层 DOM。主题通过稳定 CSS custom properties 的只读快照传入，插件样式只作用于自身页面。视图关闭
时取消对应订阅和请求；后台逻辑是否继续存在由 activation 生命周期决定。

## 插件存储与密钥

插件程序、设置、缓存、密钥和用户正文使用不同存储：

| 数据 | 位置 | 事实源 |
| --- | --- | --- |
| 插件程序 | `userData/plugins/<id>/<version>/` | 已验证发布包 |
| 用户级设置 | SQLite 或 `userData/plugin-data/<id>/` | 插件设置服务 |
| 工作区启用状态 | SQLite，可选导出到 `.tessera/` | 工作区插件状态 |
| 缓存 | 插件专属限额目录 | 可删除派生数据 |
| 密钥 | 系统安全存储 | SecretStorage |
| 文档与附件 | 用户工作区 | Markdown / 原始附件 |

插件存储 API 使用键值和大小限额，不能接受绝对路径。密钥 API 返回引用或代为执行请求，默认不把明文密钥传给插件页面。
插件卸载时询问是否保留设置；无论选择什么，都不能删除用户工作区正文。

## 安装、更新与社区目录

### 本地开发安装

首个版本提供「从本地目录加载开发插件」：

1. 用户显式选择包含 `manifest.json` 的目录。
2. 校验清单、入口、权限和兼容性。
3. 界面持续显示「开发插件」标记和实际路径。
4. 支持手动重新加载、打开日志、停用和移除链接。
5. 开发模式不降低运行时沙箱和权限检查。

工作区中的目录不能被自动发现为开发插件。符号链接解析后的目标必须记录和展示，目标变化后重新校验。

### 发布安装

```text
下载压缩包
  -> 校验下载来源、大小和 SHA-256
  -> 解压到新临时目录
  -> 拒绝路径穿越、符号链接和超额文件
  -> 校验 manifest 与入口
  -> 检查兼容性和权限变化
  -> 移动到不可变版本目录
  -> 启动健康检查
  -> 原子切换当前版本
```

插件不能自行下载或替换代码。安装器限制压缩包大小、解压后大小、文件数量和单文件大小；失败时删除临时目录，不改变当前版本。

### 社区目录

社区目录后续只保存审核索引，不承担插件运行逻辑：

```json
{
  "id": "com.example.document-history",
  "version": "1.2.0",
  "downloadUrl": "https://example.invalid/releases/1.2.0.zip",
  "sha256": "...",
  "manifestUrl": "...",
  "sourceUrl": "..."
}
```

自动检查覆盖清单、许可证、依赖锁、危险 API、CSP、包结构、哈希和兼容性。首次发布、所有权变化、系统级能力和权限显著扩大
需要人工审核。社区目录不是安全沙箱的替代物；审核遗漏时，运行时权限仍必须阻止越界。

## 失败处理与可观测性

- 清单无效：不注册贡献，不执行入口，展示具体字段错误。
- 激活超时：终止运行容器，插件进入失败状态，用户可查看日志或手动重试。
- 插件崩溃：隔离其他插件与宿主；连续崩溃达到阈值后本次会话自动停用。
- RPC 参数无效：拒绝单次调用并记录契约错误，不把内部异常堆栈返回插件。
- 权限拒绝：返回稳定错误码，插件可以降级，不得重复弹窗骚扰用户。
- 更新失败：保留当前版本和授权；新版本不参与启动。
- 自定义视图失去响应：允许单独重载或关闭视图，不阻塞文档保存与应用退出。

诊断日志记录插件 ID、版本、生命周期阶段、能力名称、资源类别、耗时、结果和错误码，不记录正文、Diff、密钥、请求体或完整
外部响应。用户可以导出单个插件的脱敏诊断包。

## 模块与契约影响面

### `packages/plugin-api`（规划新增）

提供清单类型与 Schema、`PluginContext` 公共类型、贡献点、错误码、测试替身和插件构建辅助。该包不能依赖 Electron、数据库、
应用组件或主进程实现。

### `packages/plugin-runtime`（规划新增）

提供清单校验、兼容性判断、生命周期状态机、激活事件、贡献注册、权限决策输入和 RPC 数据协议。平台无关部分留在包内，
WebContents 创建、协议注册和文件安装留在桌面应用。

### `packages/contracts`

规划增加宿主渲染层使用的插件列表、启用、禁用、开发安装、权限授权、日志查询和静态贡献契约。插件 RPC 使用独立契约命名空间，
不扩张现有 `DesktopApi` 为任意频道代理。

### `apps/desktop` 主进程

规划增加 `plugins/` 目录，负责安装目录、文件哈希、自定义协议、运行容器、发送者身份、能力网关、网络代理和崩溃回收。
工作区与文档操作复用现有安全服务，不复制路径校验逻辑。

### 渲染层与设计系统

规划增加插件管理页面、权限确认、声明式设置渲染、命令贡献注册和 `PluginViewHost`。插件管理 UI 使用设计系统公开组件；插件
不能直接导入业务应用或 Base UI。

### `packages/database`

规划保存插件安装记录、当前版本、启用范围、权限决定、设置索引和崩溃状态。插件发布包与密钥不进入 SQLite，数据库记录损坏
时可以根据安装目录重建已安装版本列表，但不能静默恢复授权。

## 安全不变量

1. 插件代码永远不在 Electron 主进程、预加载脚本或宿主 React 组件树中执行。
2. 插件身份来自运行容器与发送者映射，不来自插件请求参数。
3. 所有文件、网络、密钥、Git 和 Agent 能力在主进程逐次检查权限。
4. 工作区相对路径在主进程规范化并限制在当前工作区，插件拿不到隐式绝对路径。
5. 插件更新不能静默增加权限，插件不能自行更新代码。
6. 打开工作区不会自动安装或执行工作区携带的插件。
7. 禁用或卸载插件不能让 Markdown 正文和附件不可读。
8. 标准插件不能直接使用 Node.js、Electron、shell、原生模块或任意网络。
9. 插件失败不能阻止文档保存、关闭握手、历史恢复或应用退出。

## 验收命题

首个可执行插件版本至少覆盖：

1. 无效清单、入口越界、符号链接和压缩包路径穿越不会进入激活阶段。
2. 未激活插件不会执行代码，首次并发触发只产生一个运行容器和一次 `activate()`。
3. 插件伪造其他插件 ID、命令 ID 或资源路径不能获得额外权限。
4. 未授权的文件、网络、剪贴板和密钥请求都在主进程被拒绝。
5. 禁用、升级和崩溃后，命令处理器、事件订阅和视图资源全部撤销。
6. 插件新增权限的更新不会替换当前可用版本，直到用户明确授权。
7. 插件自定义 CSS、异常和依赖版本不能影响宿主 React 页面或其他插件视图。
8. 开发插件与发布插件使用同一运行时和权限检查，仅安装来源与重载方式不同。
9. 插件日志不包含正文、密钥、完整 Diff 或未经脱敏的外部响应。

## 实施顺序

### 阶段一：协议与内部贡献注册

- 定义清单 Schema、插件 ID、版本兼容和权限词汇。
- 建立命令、设置和通知贡献注册表。
- 用一个内置示例插件验证贡献 API，但仍随 Tessera 构建发布。
- 增加生命周期状态机和契约测试。

完成门槛：内部示例插件只能通过公开插件 API 工作，移除后不需要修改宿主功能代码。

### 阶段二：标准插件运行时与本地开发安装

- 注册 `tessera-plugin://` 协议并创建沙箱化运行容器。
- 建立发送者身份映射、RPC、超时、取消和自动资源清理。
- 实现本地开发目录选择、校验、启停、重载和日志。
- 只开放通知、命令、声明式设置、工作区元数据和只读文档。

完成门槛：恶意测试插件无法访问 Node.js、宿主 DOM、任意网络和未授权文件，崩溃不影响编辑与保存。

### 阶段三：隔离视图与受控写入

- 实现 `PluginViewHost`、主题变量和隔离视图生命周期。
- 增加工作区写入、监听、网络代理、SecretStorage 和权限升级流程。
- 将写入接入原子保存、冲突、Diff、审计和本地版本历史。
- 增加插件数据限额、诊断导出和自动崩溃停用。

完成门槛：完整自定义视图不污染宿主 UI；插件写入与人工、Agent、外部修改使用同一冲突和恢复边界。

### 阶段四：发布物、更新与社区目录

- 定义压缩包、哈希、签名或可信发布来源规则。
- 实现不可变版本安装、健康检查、原子升级和回滚。
- 建设自动扫描、人工审核、所有权与下架流程。
- 评估真实插件需求后，再决定可信桌面插件是否进入产品范围。

完成门槛：目录或发布源失效不影响已安装插件；更新失败和权限拒绝都能继续运行旧版本。

## 决策保留项

下面问题在真实内置插件和标准插件运行数据出现前不提前锁定：

- 每个插件独立 WebContents，还是低风险后台插件共享隔离进程；默认仍按独立容器设计。
- 社区发布物采用维护者签名、目录签名，还是两者同时存在。
- 工作区插件配置哪些字段允许导出到 `.tessera/`，哪些只保存在本机。
- 编辑器扩展采用声明式操作、受限 TipTap 适配层，还是单独的变换协议。
- 是否需要可信桌面插件；如果核心 Git、导入导出和外部工具能力已经足够，可能长期不开放。

这些保留项不能改变前面的安全不变量。
