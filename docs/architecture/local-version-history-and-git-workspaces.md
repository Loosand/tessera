# 本地版本历史与 Git 工作区支持

> 代码源头：`apps/desktop/src/main/index.ts`、`apps/desktop/src/preload/index.ts`、
> `apps/desktop/src/renderer/src/hooks/use-workspace.ts`、`packages/contracts/src/index.ts`、
> `packages/database/`
>
> 状态：规划。Markdown 原子保存、外部修改监听和编辑冲突处理已实现；本地版本历史、Git 状态读取、
> Git Diff 与提交尚未实现。

## TL;DR

Tessera 的工作区可能是普通文件夹，也可能是用户已经维护的 Git 仓库。前一种情况覆盖更广，用户关心的是误改后能否
找回内容；后一种情况下，用户还需要看到工作区变更并完成一次简单提交。两类需求都涉及 Diff 和历史记录，但操作对象、
存储位置与失败处理不同。

当前系统已经具备 Markdown 原子保存、磁盘版本校验、外部修改监听和关闭前保存握手。缺少的是两层独立能力：一层为每篇
文档自动保存可恢复的历史版本；另一层在工作区根目录已经存在 Git 仓库时，读取原生 Git 状态并提供文件级暂存、Diff
和提交。

这里决定分别建设「本地版本历史」与「Git 工作区支持」。二者共享 Diff 展示组件，不共享版本存储，也不把本地历史写入
用户的 `.git`。本地版本历史默认可用，采用内容寻址的不可变快照；Git 功能只接管用户已经创建的仓库，保留 Git index、
分支和远程仓库的原有语义。

## 背景与设计问题

Tessera 目前把 Markdown 作为正文事实源。人工编辑、接受 AI 建议和外部程序修改，最终都会改变同一份本地文件。现有
自动保存可以保证当前内容可靠写入，但不能回答下面几个问题：

1. 用户保存数小时后，怎样查看并恢复某个旧版本？
2. AI、批量操作或外部程序改写文档前，怎样留下可恢复的检查点？
3. 工作区已经是 Git 仓库时，怎样在不引入完整 IDE 工作流的情况下查看变更并提交？
4. 本地版本恢复与 Git 工作树变更怎样同时成立，且不互相覆盖？

这四个问题需要两套版本语义。Git 提交描述仓库级变更，由明确使用 Git 的用户管理；文档版本描述单篇内容随时间发生的
变化，应当对不了解 Git 的用户同样可用。

## 概念与能力状态

| 概念 | 定义 | 用户是否需要理解 Git | 当前状态 |
| --- | --- | --- | --- |
| 本地版本历史 | 单篇文档的自动检查点、命名版本、比较与恢复 | 否 | 规划 |
| 检查点 | 一次不可变的文档内容快照及其时间、来源和父版本 | 否 | 规划 |
| 恢复版本 | 将旧版本内容重新写成当前文档，并保留恢复前后的历史 | 否 | 规划 |
| Git 工作区支持 | 对工作区根目录现有 Git 仓库读取状态、展示 Diff、暂存文件和提交 | 是 | 规划 |
| Git 远程同步 | fetch、pull、push、认证和冲突解决 | 是 | 待确定，不属于首个版本 |

## 目标与非目标

### 目标

1. 普通工作区默认获得不依赖 Git 的文档历史。
2. 版本恢复不会删除后来产生的版本，也不会覆盖唯一历史副本。
3. AI 写入、外部修改和批量变更使用同一套检查点协议。
4. 已有 Git 仓库可以查看文件变更树、文件 Diff、暂存状态和提交结果。
5. 两套能力都经过主进程和类型化 IPC，渲染层不直接访问文件系统或执行 Git 命令。
6. 当前 Markdown 始终是可读、可编辑、可导出的正文事实源。

### 非目标

- 不建设分支创建与切换、rebase、cherry-pick、stash、tag 和提交图。
- 不建设 GitHub、GitLab、Pull Request 或 Issue 客户端。
- 不在首个版本内实现逐行暂存和可视化冲突编辑器。
- 不自动为普通工作区执行 `git init`，也不自动添加远程仓库。
- 不自动提交或推送用户已有的 Git 仓库。
- 不把普通用户的文档历史伪装成 Git commit、branch 或 checkout。
- 不把历史正文只保存到 SQLite。

## 总体边界

```text
人工编辑 / AI 修改 / 外部修改
              |
              v
       工作区写入服务
       |             |
       |             +----> 历史服务 ----> .tessera/history/
       v                         |
  当前 Markdown                  +----> SQLite 派生时间线索引

工作区根目录已有 Git 仓库
              |
              v
       Git 仓库服务 ----> 系统 Git ----> 用户原有 .git
              |
              +----> 变更树 / Diff / 暂存 / 提交
```

历史服务记录 Tessera 能解释的文档生命周期。Git 仓库服务读取和修改用户原有 Git 仓库。恢复本地版本会改变当前 Markdown，
因此随后会正常出现在 Git 工作树中；Git 提交不会替代本地检查点。

## 本地版本历史

### 产品语义

版本历史位于文档详情侧栏，按时间倒序显示。每一项至少提供：

- 创建时间；
- 来源：自动保存、手动命名、AI 修改、外部修改、导入或恢复；
- 可选名称与操作说明；
- 与当前内容比较；
- 查看完整版本；
- 复制内容；
- 恢复为当前版本。

恢复操作遵循下面的顺序：

```text
读取目标版本
  -> 为当前内容强制创建「恢复前」检查点
  -> 展示目标版本与当前内容的 Diff
  -> 用户确认
  -> 通过工作区原子写入协议更新 Markdown
  -> 创建来源为「恢复」的新版本
```

恢复产生新的当前版本。目标版本之后的历史仍然保留，用户可以再次比较或恢复。

### 检查点策略

检查点不能跟随每次按键创建，也不能只在应用关闭时创建。首个实现采用下面的规则：

1. 文档首次进入历史系统时，记录当前磁盘内容作为基线版本。
2. 原子保存成功且内容哈希变化后，更新待记录内容；距离上一自动检查点达到 5 分钟时写入新检查点。
3. 编辑器关闭或工作区关闭时，如果当前保存内容尚未形成检查点，则写入一次检查点。
4. 接受 AI 修改、执行批量替换、导入覆盖和版本恢复前，强制记录当前内容。
5. 外部修改覆盖当前磁盘内容时，先记录 Tessera 最后确认的内容，再记录接受后的外部版本。
6. 内容哈希相同的版本不重复保存正文对象；允许补充名称、来源或关联信息。

自动检查点保留策略暂不做静默删除。首个版本需要提供历史占用空间统计；经过真实工作区数据评估后，再决定按时间密度
压缩或设置空间预算。手动命名版本和破坏性操作前检查点不得被自动清理。

### 文档身份与重命名

版本历史使用稳定的 `documentId`，不能只用相对路径作为身份。

- Tessera 内部重命名时更新 `documentId -> relativePath` 映射，历史链保持不变。
- 删除文档后保留历史记录，并标记当前路径已不存在。
- 从历史恢复已删除文档时，用户选择恢复路径；恢复结果继续使用原 `documentId`。
- 外部程序完成的重命名在首个版本中可以表现为删除与新建；后续可以结合文件标识和内容哈希增加匹配策略。

### 持久化格式

历史事实保存在工作区内的 `.tessera/history/`，SQLite 只保存可重建的时间线索引和查询状态。

```text
.tessera/history/
  version.json
  manifest.json
  objects/
    ab/<sha256>.br
  versions/
    <document-id>/<version-id>.json
```

正文对象使用 SHA-256 内容寻址和 Brotli 压缩。相同内容只写入一次。版本记录至少包含：

```ts
interface DocumentVersionRecord {
  version: 1
  id: string
  documentId: string
  parentId: string | null
  relativePath: string
  contentHash: string
  createdAt: string
  source: "baseline" | "autosave" | "manual" | "ai" | "external" | "import" | "restore"
  label: string | null
  relatedGitCommit: string | null
}
```

对象和版本记录先写临时文件，再通过同目录原子替换发布。`manifest.json` 损坏时，可以根据 `versions/` 重建文档映射；
对象缺失或哈希不符时，该版本标记为损坏，不能用空内容替代。

### 外部修改与 AI 写入

外部修改仍沿用现有冲突协议：存在未保存草稿时暂停自动保存，由用户选择保留本地内容、接受外部内容或比较差异。版本历史
为两个候选内容提供检查点，但不能替用户自动解决冲突。

Agent 修改在应用写入前创建检查点。用户批准 Diff 后，写入结果创建来源为 `ai` 的版本，并记录操作 ID；版本记录不保存
模型密钥、完整对话或无法从审计记录解释的隐式状态。

## Git 工作区支持

### 启用条件

Git 能力只在下面条件同时满足时启用：

1. `git rev-parse --show-toplevel` 返回的规范路径与工作区根目录一致；位于更大仓库的子目录不自动接管。
2. 系统 Git 可执行文件可用。
3. 仓库不处于 Tessera 无法安全解释的操作中，例如未完成的 rebase。

Tessera 不因读取工作区状态而创建仓库、修改 remote、切换分支或提交文件。分支名称和 remote 在首个版本中只读展示。

### 首个版本的界面

Git 面板提供四组信息：

1. 仓库摘要：当前分支、仓库根目录、ahead/behind 和进行中的 Git 操作。
2. 变更树：已暂存、未暂存、未跟踪和冲突文件，保留目录层级与状态标记。
3. Diff：工作树与 index、index 与 `HEAD` 两种文件级比较。
4. 提交：提交已暂存文件，要求非空提交说明，并显示成功提交的短 hash。

暂存概念在界面中保留，因为 Git commit 只提交 index。Tessera 可以把它表达为「将文件加入本次提交」和「从本次提交移除」，
首个版本只支持整个文件，不支持逐行或逐块暂存。

### Git 操作边界

首个版本允许调用：

- `git status --porcelain=v2 -z --branch`
- `git diff -- <path>`
- `git diff --cached -- <path>`
- `git add -- <path...>`
- `git restore --staged -- <path...>`
- `git commit -m <message>`
- `git log` 与 `git show` 的只读查询

首个版本不调用 `checkout`、`switch`、`reset --hard`、`clean`、`merge`、`rebase`、`push` 或 `pull`。检测到冲突、
detached HEAD、进行中的 merge/rebase 或无法解析的 index 状态时，界面展示原因并停止写操作；用户仍可复制诊断信息或在
终端中打开工作区。

Git 子进程由主进程启动，使用参数数组，不拼接 shell 命令。每个调用设置超时、标准输出上限和标准错误脱敏；IPC 只接受
经过工作区路径校验的相对路径，不能接受任意 Git 参数。

### 与 `.tessera` 的关系

内部版本历史不能进入用户的 Git 提交。检测到工作区是 Git 仓库后，Tessera 通过
`git rev-parse --git-path info/exclude` 找到仓库本地排除文件并加入 `.tessera/`，不修改用户共享的 `.gitignore`。
这种路径解析同时适用于普通仓库和 Git worktree。如果 `.tessera/` 已经被跟踪，Tessera 只提示风险，不自动执行
`git rm --cached`。

## 两套能力的协作规则

| 场景 | 本地版本历史 | Git 工作区 |
| --- | --- | --- |
| 普通自动保存 | 按检查点策略记录 | 显示为未暂存变更 |
| AI 修改 | 记录修改前检查点和 AI 来源版本 | 显示普通文件 Diff |
| 恢复旧版本 | 保留恢复前版本并创建恢复版本 | 显示普通文件 Diff |
| Git commit | 历史内容不变，可为相邻版本补充 commit hash | 提交 index 中的文件 |
| 外部 Git checkout/pull | 按外部修改协议记录新旧内容 | 重新读取仓库状态 |
| 删除文档 | 保留可恢复历史 | 显示删除状态 |

共享层只包含 Diff 计算结果和展示模型。历史服务不能通过 Git commit 查询自己的版本，Git 服务也不能读取历史对象来改变
工作树。

## 模块与 IPC 影响面

### `packages/contracts`

规划增加两组窄接口：

- 历史：版本摘要、版本正文、版本 Diff、命名检查点、恢复请求和存储统计。
- Git：仓库摘要、变更条目、文件 Diff、文件级暂存、移出暂存和提交请求。

所有请求携带工作区会话和相对路径。恢复、暂存和提交属于写操作，需要返回更新后的磁盘版本或仓库状态。

### `packages/core`

规划增加与平台无关的检查点策略、版本来源模型、恢复编排和 Diff 展示模型。内容压缩、文件锁和 Git 子进程不进入
`packages/core`。

### `apps/desktop` 主进程

规划增加：

- `history/`：内容对象、版本记录、manifest 重建、检查点和恢复服务；
- `git/`：仓库检测、porcelain 状态解析、Diff、暂存和提交适配器；
- 工作区写入成功后的历史钩子；
- 文件监听与 Git 状态刷新事件；
- 带取消、超时和输出上限的后台任务。

### `packages/database`

规划增加可重建的版本时间线索引和 Git 状态缓存。数据库损坏不能导致历史对象、版本记录、Markdown 或 Git index 丢失。

### 渲染层与设计系统

规划增加文档版本时间线、版本 Diff、Git 变更树和提交表单。版本 Diff 与 Git Diff 共享行级、区块级展示组件，但标题、
操作按钮和状态文案分别表达「恢复文档」与「提交 Git 变更」。

## 失败处理

- 历史写入失败：Markdown 保存仍可成功，但界面显示历史未记录状态并允许重试；不能把保存失败伪装成成功。
- 历史对象损坏：禁止恢复，显示缺失对象和版本 ID；其他版本继续可用。
- 恢复期间磁盘版本变化：沿用文档写入冲突协议，不覆盖外部内容。
- Git 命令超时：终止子进程，保留 index 和工作树，重新读取状态。
- Git commit 失败：展示 Git 返回的脱敏错误，不自动重试或更改分支。
- 仓库进入冲突或 rebase：所有 Tessera Git 写操作禁用，只保留状态、Diff 和诊断入口。

## 可观测性与评测

诊断日志只记录版本 ID、文档 ID、相对路径、内容大小、耗时、Git 子命令类别和退出状态，不记录正文、Diff、提交说明、
remote 凭据或环境变量。

本地版本历史至少覆盖下面的验收命题：

1. 连续编辑只产生符合时间窗口的检查点，相同内容不重复占用对象空间。
2. 应用内重命名、删除和恢复后，文档身份与历史链保持稳定。
3. 恢复旧版本后，恢复前后的版本都能继续读取和比较。
4. manifest、SQLite 索引或单个对象损坏时，失败范围被限制且可以重建可恢复部分。
5. AI、外部修改和关闭前保存都能触发对应来源的检查点。

Git 工作区支持至少覆盖下面的验收命题：

1. 普通目录、仓库根目录和仓库子目录得到不同且可解释的状态。
2. 已暂存、未暂存、未跟踪、重命名、删除和冲突文件被稳定解析。
3. 文件名包含空格、换行或非 ASCII 字符时，不发生参数注入或路径错配。
4. Tessera 暂存或移出暂存一个文件时，不改变其他文件现有的 index 状态。
5. 提交失败、Git 锁存在或仓库处于 merge/rebase 时，不执行补偿性破坏操作。
6. `.tessera/` 不进入新提交，且不会自动移除用户已经跟踪的文件。

## 实施顺序

### 阶段一：历史存储与恢复

- 定义版本契约、内容对象和检查点策略。
- 接入现有原子保存、关闭握手与应用内重命名。
- 实现文档时间线、版本查看、Diff 和恢复。
- 增加索引重建、损坏隔离和存储统计。

验收条件：普通 Markdown 工作区无需 Git 即可查看、比较并恢复历史版本。

### 阶段二：AI 与外部修改检查点

- 在 AI 写入、批量变更和导入覆盖前创建检查点。
- 把外部修改冲突的两个候选内容接入历史记录。
- 记录来源、操作 ID 和可解释的审计关联。

验收条件：应用内所有可改变正文的入口都能说明修改来源，并能恢复修改前内容。

### 阶段三：轻量 Git 工作区支持

- 实现仓库检测、状态解析、变更树和两类文件 Diff。
- 实现文件级暂存、移出暂存和提交。
- 接入文件监听、状态刷新、超时与错误展示。

验收条件：已有 Git 仓库可以在 Tessera 内完成「查看变更 -> 选择文件 -> 查看 Diff -> 提交」，且不需要分支管理界面。

### 阶段四：根据使用数据决定远程能力

fetch、pull、push、认证和冲突解决保持待确定。只有本地提交使用稳定、用户明确需要远程操作，并且失败恢复协议可被验证后，
才进入下一阶段。

## 待确认决策

- 自动检查点的长期保留密度和工作区空间预算。
- 二进制附件是否进入本地版本历史，以及单文件大小上限。
- 外部重命名的文档身份匹配策略。
- 是否提供手动导出或迁移 `.tessera/history/` 的工具。
- Git 远程操作是否属于 Tessera，还是始终交给系统 Git 客户端。
